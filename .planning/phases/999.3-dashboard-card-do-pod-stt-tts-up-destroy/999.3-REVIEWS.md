## Gemini Review

This review covers the implementation plans for **Phase 999.3: Dashboard — card do pod STT/TTS (up→destroy)**.

### Summary
The plans for Phase 999.3 are exceptionally well-structured and technically sound, leveraging existing architectural patterns to integrate the RTX 3060 pod visibility into the AI Dashboard. The design correctly positions the gateway as a "dumb pipe" for the pod's state blob, ensuring the Go backend doesn't need to mirror the complex internal schema of the Python management script. The inclusion of manual control buttons with owner-gating and audit logging aligns perfectly with the project's security standards, and the "night-gap" cost accrual logic shows high attention to detail regarding operational accuracy.

### Strengths
*   **Architectural Decoupling:** Using `json.RawMessage` in the gateway to handle the script's state blob prevents schema duplication and keeps the gateway implementation lean and maintainable.
*   **Robust Cost Accrual:** The cost accumulation logic in the Python script is sophisticated, correctly handling day/month rollovers and ensuring the idle night period (22:00–07:00) isn't erroneously billed.
*   **Fail-Soft Dashboard Aggregation:** The extension of the `OperationsHandler` is resilient; a Redis failure or missing data for the 3060 pod will not affect the other critical dashboard panels (FSM, Breakers, Primary Cost).
*   **Security & Audit Compliance:** Manual commands are protected by `requireOwner` gates and server-side whitelists, and are tracked in the `admin_audit_log`, maintaining the project's high security bar.
*   **Atomic Command Consumption:** Utilizing Redis `GetDel` ensures that commands are consumed exactly once, preventing race conditions or unintentional double-executions.

### Concerns
*   **Portainer Deploy Risk (Severity: MEDIUM):** Updating the gateway stack (38) via Portainer PUT requires manually preserving 76 environment variables. A mistake here could break the entire gateway. Plan 07 Task 2 correctly identifies this as a critical step, but it remains the most fragile part of the rollout.
*   **Redis Volatility (Severity: LOW):** Production Redis has no persistence. A Redis restart will clear the 3060 pod state until the next 2-minute poll. The plan successfully mitigates this by distinguishing "awaiting publication" from "stale data" in the UI.
*   **Command Feedback Loop (Severity: LOW):** Because the script polls every 2 minutes, there is a delay between clicking a button and seeing the "executando" status. While acceptable for this internal tool, it's worth noting as a minor UX friction point.

### Suggestions
*   **Audit Metadata Clarity:** In `sttPodCommandCore` (Plan 04), ensure the audit metadata includes the target pod identifier (e.g., the current `machine_id` from the state) to provide better context in the incident logs.
*   **SQL Verification Precision:** In Plan 06 Task 2, explicitly verify the schema name (`ai_gateway` vs `public`) against the `gateway/db` files before running the production SQL query to avoid "table not found" errors during verification.
*   **Script Log Rotation:** While the script uses `LOG_PATH`, ensure that standard systemd logging (journald) is also capturing the `print` outputs as a backup for the manual log file.

### Risk Assessment: LOW
The phase is primarily additive and follows proven patterns established in Phases 13, 17, and 18. The logic is well-isolated, and the gateway changes are non-breaking. The most significant risks are operational (Portainer deployment), which are adequately managed by the detailed verification script and the manual checkpoint.

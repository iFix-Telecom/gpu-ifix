## Summary

Esta fase tem três frentes que quase não se tocam, e a maior parte do risco está numa
só: o script Python. O **gateway** ganha dois handlers admin triviais (POST state / POST
command) que são pipes burros pro Redis, mais 1 campo novo no `OperationsResponse` —
tudo cai exatamente no molde `tenants_admin_http.go` (interface isolada, construtor
duplo, envelope OpenAI, contador `obs.GatewayAdminRequests` por branch). O **dashboard**
ganha 1 componente de painel + 1 tipo TS + 2 server actions owner-gated, clonando
`updatePodConfigCore` 1:1; a única mudança estrutural é que `/operacao/page.tsx` hoje é
`"use client"` e precisa virar RSC-shell (pra ler `getViewerRole()`) com o corpo atual
movido pra um client island — exatamente o que `/operacao/config/page.tsx` já faz. O
**script** `ops/vast-3060/vast3060.py` é onde mora o trabalho real: hoje o `state.json`
tem 7 campos (`instance_id, machine_id, ip, port, fail_count, machine_avoid,
alerted_no_offer`) e **não tem nada** de dph, geolocation, timestamp de provisão, custo
acumulado nem lista de eventos. Tudo isso é campo NOVO, escrito em ~6 pontos de evento
já existentes no fluxo (`provision` sucesso/bail/no-offer, `cmd_stop`, `cmd_ensure`).

Duas descobertas mudam o escopo planejado. **(1)** O todo `incidents-history-date-filter-search`
está **100% implementado** — o handler `audit.go` já aceita `from`/`to`/`search` e retorna
`Total` (COUNT real), `fetchAudit` já os encaminha, e `/incidents/page.tsx` já tem
date-range picker (`react-day-picker`) + search box + pager por `total`. Os 4 checkboxes
do todo estão fechados pela Phase 15/OBS-10. Isso elimina o "plano extra" previsto no
CONTEXT e o reduz a uma verificação. **(2)** O Redis do gateway em PROD roda com
`appendonly no` e `save ""` — **sem persistência nenhuma**. A chave `gw:sttpod:state`
sem TTL (D-03) desaparece num restart do Redis. Isso não invalida D-03, mas obriga o
desenho a ter republicação frequente: o poll de comando de 1-2min (D-10) deve ser o
MESMO request que republica o heartbeat, encurtando a janela de card-vazio de 15min pra
≤2min sem código extra.

O caminho mais curto pro consumo de comando (D-09/D-10/D-12) é a resposta do próprio
`POST /admin/sttpod/state` devolver `{"pending_command": …}` — o gateway faz `GETDEL` em
`gw:sttpod:command` e entrega. Isso satisfaz "script consome" sem expor Redis (D-01),
sem endpoint GET novo, e sem inventar canal de status (D-12): o "pendente" no card sai
da mesma chave lida pelo `OperationsHandler` antes de ser consumida, e o "executado às
HH:MM" sai do `last_command_result` que o script ecoa no publish seguinte.

**Primary recommendation:** Gateway = pipe burro (armazena/devolve o blob do script
verbatim como `json.RawMessage`, sem duplicar 20 campos numa struct Go); toda a
semântica (custo, eventos, agenda, uptime) mora no script; dashboard só formata.
`GETDEL` no consumo do comando. Poll de 1-2min republica heartbeat E busca comando no
mesmo POST.

### Alternatives Considered

| Instead of | Could Use | Tradeoff |
|------------|-----------|----------|
| Blob `json.RawMessage` no Go | Struct Go tipada com ~20 campos | Struct dá validação + testes de forma, mas duplica o schema em 3 lugares (Python → Go → TS) sem o gateway usar NENHUM campo. D-05 diz explicitamente "gateway guarda o JSON inteiro". **Escolher RawMessage.** |
| `GETDEL` no POST de state | `GET /admin/sttpod/command` separado + delete explícito | Endpoint a mais, 2 round-trips, e um delete que pode falhar sozinho. GETDEL é atômico e cabe na resposta que o script já vai receber. **Escolher GETDEL** (custo: se o script morrer entre GETDEL e execução, o comando some — operador reclica). |
| Script converte USD→BRL | Gateway multiplica por `cfg.USDToBRLRate` ao servir | Se o script tiver seu próprio rate, ele diverge do painel de custo do primário (D-08 pede consistência). **Script acumula USD; gateway deriva BRL.** |

### Pattern 1: Handler admin POST (molde `tenants_admin_http.go`)

**What:** Todo handler admin novo segue o mesmo esqueleto: constante de rota, deps
isoladas, construtor duplo (prod + teste), decode do body, envelope de erro OpenAI via
`httpx.WriteOpenAIError`, e `obs.GatewayAdminRequests.WithLabelValues(route, "2xx"|"4xx"|"5xx").Inc()`
em **cada** branch de saída.

**When to use:** os dois handlers novos desta fase.

```go
// Source: gateway/internal/admin/tenants_admin_http.go:107-143 (verbatim pattern)
const sttPodStateRoute = "/admin/sttpod/state"

func (h *SttPodHandler) PostState(w http.ResponseWriter, r *http.Request) {
	// Cap PRÓPRIO — o cap global é 25 MiB (config.go:365), grande demais
	// para um blob de status que cabe em ~30 KB.
	body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, sttPodMaxBodyBytes))
	if err != nil {
		h.badRequest(w, "payload_too_large", "state payload excede o limite")
		return
	}
	if !json.Valid(body) {
		h.badRequest(w, "invalid_body", "request body is not valid JSON")
		return
	}
	if err := h.rdb.Set(ctx, redisx.SttPodStateKey(), body, 0).Err(); err != nil { … 5xx … }

	// GETDEL: entrega + consome o comando pendente no MESMO round-trip (D-09/D-10).
	cmd, err := h.rdb.GetDel(ctx, redisx.SttPodCommandKey()).Bytes()
	// redis.Nil => sem comando pendente => pending_command: null
	…
	w.WriteHeader(http.StatusOK)
	_ = json.NewEncoder(w).Encode(map[string]any{"pending_command": raw})
	obs.GatewayAdminRequests.WithLabelValues(sttPodStateRoute, "2xx").Inc()
}
```

### Pattern 2: Chaves Redis via `redisx` (prefixo `gw:`)

**What:** nomes de chave nunca são literais espalhados — cada subsistema declara
constantes privadas + funções exportadas no pacote `redisx`.

```go

	sttPodStateKey   = "gw:sttpod:state"
```

**Nota de escopo (ponytail):** `shed.go` embrulha cada operação numa função helper
(`WriteShedState`, `ReadShedState`…). Para 2 chaves e 4 operações triviais isso é
cerimônia; basta declarar as constantes/getters em `redisx` (para o namespace ficar
auditável num lugar só) e chamar `rdb.Set/Get/GetDel` direto no handler, que já tem o
`ctx` com timeout do request.

### Pattern 3: Extensão do `OperationsResponse` fail-soft

**What:** cada seção do `/admin/operations` degrada sozinha — `rec == nil` vira
`"unknown"`, `breakers == nil` vira slice vazio, erro de tz não derruba o request
(`operations.go:299-308`). O campo `sttpod` segue a mesma regra: Redis fora do ar ou
chave ausente ⇒ `sttpod: null`, **nunca** 500. O card mostra "sem publicação ainda".

```go
type SttPodSection struct {
	// Blob verbatim publicado pelo script (D-05) — o gateway não interpreta.
	State json.RawMessage `json:"state"`
	// Comando ainda não consumido pelo script (D-12) — null quando não há.
	PendingCommand json.RawMessage `json:"pending_command"`
}

// resp.SttPod é *SttPodSection com `omitempty`: nil quando nem state nem
// command existem. NÃO propagar erro de Redis para o status HTTP.
```

### Pattern 4: Server action owner-gated (molde `createTenantCore`)

**What:** ordem fixa e não-negociável — `requireOwner` **primeiro await** → validação
server-side (whitelist) **antes** de qualquer chamada ao gateway → `gatewayAdminPost`
(server-only, X-Admin-Key) → **exatamente 1** `writeAuditLog` → `revalidatePath`.
O wrapper `"use server"` chama `requireOwner()` **sem argumento** (identidade só da
sessão — CR-01) e delega ao `*Core`.

```ts
// Source: dashboard/src/lib/admin-actions-core.ts:690-723 (createTenantCore, verbatim shape)
const STTPOD_COMMANDS = new Set(["provision", "destroy"]);

export async function sttPodCommandCore(args: {
  actor?: Actor; auth?: AuthLike; db?: unknown;
  command: string; deps?: TenantMutationDeps;
}): Promise<void> {
  const authInstance = args.auth ?? (realAuth as unknown as AuthLike);
  const { actor } = await requireOwner(args.actor, authInstance);   // 1º await

  if (!STTPOD_COMMANDS.has(args.command)) {
    throw new Error('Comando inválido — use "provision" ou "destroy".');
  }

  const post = args.deps?.post ?? realGatewayAdminPost;
  await post("sttpod/command", { command: args.command });

  await writeAuditLog({
    db: args.db,
    actor: { id: actor.id, email: actor.email },
    action: `sttpod.${args.command}`,
    metadata: { command: args.command },
  });

  safeRevalidateOperacao();   // revalidatePath("/operacao") dentro de try/catch
}
```

### Pattern 6: Acumulador de custo no script (D-07)

**What:** acumulação incremental por delta de tempo, com rollover BRT de dia e mês.
Chamado em toda publicação (poll de 2min ⇒ granularidade de 2min, erro desprezível).
`datetime.now()` do ops-claude JÁ é America/Sao_Paulo `[VERIFIED: timedatectl]` — mesmo
fuso que o gateway usa em `operations.go:187`.

```python
def accrue_cost(st: dict, now_ts: float) -> None:
    """Acumula custo USD desde o último tick. Puro o suficiente pra testar."""
    c = st.setdefault("cost", {"day": "", "day_usd": 0.0,
                               "month": "", "month_usd": 0.0, "last_ts": None})
    today = datetime.fromtimestamp(now_ts).strftime("%Y-%m-%d")
    month = today[:7]
    if c["day"] != today:
        c.update(day=today, day_usd=0.0)
    if c["month"] != month:
        c.update(month=month, month_usd=0.0)
    last, dph = c["last_ts"], st.get("dph")
    if last and dph and st.get("instance_id"):
        hours = max(0.0, (now_ts - last) / 3600.0)
        c["day_usd"] += dph * hours
        c["month_usd"] += dph * hours
    c["last_ts"] = now_ts
```

**Guarda obrigatória:** só acumula quando `instance_id` está setado — senão o gap
noturno (22:00→07:00, instância destruída) seria cobrado. `cmd_stop` já faz
`st.update(instance_id=None, …)` (`vast3060.py:428`), então o guard funciona de graça,
mas o `last_ts` precisa ser atualizado no stop para não gerar um delta gigante na
primeira publicação da manhã.

### Anti-Patterns to Avoid

- **Struct Go tipada espelhando o blob:** duplica o schema em 3 linguagens sem o gateway
  ler nenhum campo. Contraria D-05. Use `json.RawMessage`.
- **`fail_count` como sinal:** o campo existe no `state.json` mas é vestigial — só é
  escrito como `0` em 3 lugares (`vast3060.py:377,391`) desde a virada up→destroy. Não
  construir UI em cima dele; se aparecer no payload, é ruído.
- **Erro de Redis virando 500 no `/admin/operations`:** derruba os outros 4 painéis por
  causa do 5º. Fail-soft obrigatório.
- **Botão sem `requireOwner` no server action:** o gate de UI é cosmético por
  construção (`viewer.ts` docstring). O `*Core` DEVE re-checar.
- **Reusar o timer do `ensure` pro poll de comando:** ensure de 2min multiplica por 7,5
  as chamadas à Vast API e reescreve semântica testada em drill E2E. Timer separado.
- **Colocar `machine_avoid` como badge estático sem contexto:** o card existe pra
  responder "por que a oferta barata foi pulada?" (CONTEXT §Specifics). A lista precisa
  vir com o `machine_id` de cada evento de falha correlacionável no histórico.

## Common Pitfalls

### Pitfall 1: Redis sem persistência apaga o "último estado conhecido"
**What goes wrong:** D-03 promete "último estado conhecido sempre visível" com chave sem
TTL. Mas `appendonly no` + `save ""` significam que qualquer restart do container
`ai-gateway-prod_redis` zera o keyspace — o card fica vazio até a próxima publicação.
**Why it happens:** o Redis do gateway é tratado como espelho descartável por design
(`redisx/shed.go:13` — "o FSM in-process é autoritativo; Redis é só espelho"). O
`gw:sttpod:state` quebra essa premissa: aqui o Redis é a ÚNICA cópia no lado do gateway.
**How to avoid:** (a) o poll de comando de 1-2min **republica o heartbeat** no mesmo POST
— janela de card-vazio ≤2min em vez de ≤15min, custo zero; (b) o card distingue
`sttpod: null` ("sem publicação — aguardando próximo ciclo") de `published_at` velho
("stale há Xmin"), textos diferentes; (c) a fonte-verdade permanece o `state.json` em
disco no ops-claude, que sobrevive a tudo.
**Warning signs:** card vazio logo após um deploy do stack 38 (o PUT recria o serviço
redis se o compose mudar).

### Pitfall 2: `/operacao/page.tsx` é `"use client"` — `getViewerRole()` não roda lá
**What goes wrong:** tentar `const isOwner = await getViewerRole()` dentro da página
atual: `next/headers` não existe no bundle do cliente ⇒ erro de build.
**Why it happens:** a página nasceu como painel read-only puro (quick 260625-v04); a
Phase 17 resolveu o mesmo problema criando `/operacao/config` como RSC separada.
**How to avoid:** split RSC-shell + client island (Pattern 5). É 1 arquivo novo e um
`git mv` conceitual do corpo — não reescrever a lógica de query/loading/erro.
**Warning signs:** `You're importing a component that needs next/headers`.

### Pitfall 3: Corrida entre GETDEL e execução do comando
**What goes wrong:** o gateway faz GETDEL, o script recebe o comando e morre (OOM,
reboot, exception no meio) antes de executar ⇒ comando perdido silenciosamente; o card
mostra "sem comando pendente" e o operador acha que executou.
**Why it happens:** GETDEL consome antes da confirmação de execução (at-most-once).
**How to avoid:** (a) o script grava `last_command_result` no `state.json` **antes** de
executar, com `status: "running"`, e atualiza pra `ok/fail` depois — assim o card mostra
"executando…" e nunca some sem rastro; (b) marcar a simplificação com comentário
`ponytail:` explicitando o teto (at-most-once) e o upgrade (ACK explícito). Com botão
manual + operador olhando, reclicar é o recovery aceitável.
**Warning signs:** operador reclamando "cliquei e não aconteceu nada".

### Pitfall 4: Acumulador de custo cobra o gap noturno
**What goes wrong:** delta = `now − last_ts` sem guarda ⇒ o primeiro tick das 07:00
credita 9 horas de pod que não existiu (22:00→07:00 sem instância).
**Why it happens:** `cmd_stop` (`vast3060.py:420-430`) limpa `instance_id/ip/port` mas
não toca em nenhum timestamp de acumulação.
**How to avoid:** acumular **somente** com `instance_id` setado, E atualizar `last_ts`
em toda publicação (inclusive as que não acumulam). Ambas as condições — só uma delas
não basta.
**Warning signs:** `cost_day_usd` acordando com valor ~0,25 (9h × $0,03) às 07:00.

### Pitfall 5: `machine_avoid` cresce sem limite e envenena a busca
**What goes wrong:** já tem 5 máquinas `[VERIFIED: state.json]` e só cresce (append em
`bail`, `vast3060.py:324-327`); nunca é podada. A busca `pick_offer` filtra por ela
(`:264`), então o pool encolhe monotonicamente até secar o mercado — exatamente o
incidente de 2026-07-25 que motivou o teto elástico.
**Why it happens:** a decisão de 2026-07-25 (comentário em `:386-389`) foi deliberada:
só máquinas que **falharam provision** entram no avoid permanente.
**How to avoid nesta fase:** **NÃO mexer na semântica** — está fora do escopo (o card só
EXIBE a lista, D-14). Mas exibir com o timestamp da falha correspondente do histórico dá
ao operador o dado pra decidir podar manualmente. Se surgir vontade de auto-expirar,
é ideia nova → backlog, não esta fase.
**Warning signs:** `PROVISION abortado: nenhuma oferta elegível (mesmo com teto 2x)` no
log com `avoid` de 10+ máquinas.

### Pitfall 6: Publicar de dentro do `provision()` sem try/except derruba o provision
**What goes wrong:** o `provision()` tem caminhos críticos (flip do stack, destroy da
velha). Um `publish()` que levante exceção no meio deixa a migração pela metade — pior
que não ter card nenhum.
**Why it happens:** `http()` no script já engole exceções e devolve `(0, msg)`
(`vast3060.py:101-102`), mas `http_json` + acesso a `env['GW_ADMIN_KEY']` podem levantar
`KeyError` se o secret não foi adicionado no host.
**How to avoid:** `publish()` best-effort com `try/except` amplo + `log()`, exatamente
como `notify()` já faz (`vast3060.py:161-170`, docstring: "nunca derruba o fluxo por
falha de notificação"). Copiar esse contrato literalmente.
**Warning signs:** provision abortando com traceback logo após o deploy do script novo.

### Pitfall 7: Deploy esquecido do `/opt/vast-3060/vast3060.py`
**What goes wrong:** merge no `develop`, gateway e dashboard deployados, card no ar
mostrando "sem publicação" pra sempre — porque as units systemd executam
`/opt/vast-3060/vast3060.py`, não o arquivo do repo.
**Why it happens:** o script não tem pipeline de deploy (CONTEXT §Integration Points:
"script = ops-claude local (sem deploy pipeline)").
**How to avoid:** passo explícito de deploy no plano: `cp` + `daemon-reload` + `enable
--now` do timer novo + 1 `vast3060.py poll` manual pra provar o publish.
**Warning signs:** `diff /opt/vast-3060/vast3060.py ops/vast-3060/vast3060.py` não-vazio.

### Pitfall 8: Cap de body herdado é 25 MiB
**What goes wrong:** o router inteiro é embrulhado em `http.MaxBytesHandler(r, cfg.MaxBodyBytes)`
com `MaxBodyBytes = 25 MiB` (`config.go:365`, dimensionado pro limite de áudio da OpenAI).
Um blob malformado ou um `events[]` sem cap pode escrever megabytes no Redis.
**How to avoid:** `http.MaxBytesReader` próprio no handler (256 KiB é folgado: 50 eventos
× ~200 B ≈ 10 KB) + cap de 50 eventos **no script** (D-06) como primeira linha.

   - O que sabemos: o script já fala com `https://ai-gateway.converse-ai.app/v1/*`; o admin key é usado do ops-claude via curl pro mesmo host segundo o CLAUDE.md (`curl -H "X-Admin-Key: …" https://ai-gateway.converse-ai.app/admin/metrics`).

   - Recomendação: 1 `curl` de smoke no início da execução (`GET /admin/metrics` com a key) antes de escrever o `publish`. Se falhar, usar `http://10.10.10.50:80` + `Host:` header (o script está na mesma rede NAT).

2. **Poll de 2min deve rodar fora da janela 07-22?** — RESOLVED: timer alinhado à janela (`07..21:00/2:00`), implementado no Plano 999.3-03.
   - O que sabemos: o `ensure` só age dentro da janela (`vast3060.py:407-408`); um `provision` manual às 23h seria desfeito pelo `stop` já executado.

3. **`published_at` em UTC ou BRT?** — RESOLVED: RFC3339 com offset via `now_rfc3339()`, Plano 999.3-03 Task 1.
   - Recomendação: RFC3339 **com offset** (`datetime.now().astimezone().isoformat()`) — o ops-claude é `-03` e o `Date` do JS parseia offset corretamente. Evita a classe de bug documentada em `incidents/page.tsx:44-54`.

   - Recomendação: `systemctl reset-failed` no passo de deploy. Cosmético, mas polui `systemctl --failed` e confunde diagnóstico futuro.

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Operator dispara destroy do pod (privilege escalation) | Elevation of Privilege | `requireOwner` no `*Core`; wrapper `"use server"` chama `requireOwner()` **sem args** (CR-01) — o caller não pode afirmar o próprio role |
| Command injection via campo `command` | Tampering | Whitelist `Set(["provision","destroy"])` no dashboard + revalidação no handler Go; o script faz `if cmd == "provision"` — **nunca** `subprocess`/`eval` com valor recebido |
| Blob gigante enchendo o Redis (DoS) | Denial of Service | `MaxBytesReader` 256 KiB no handler + cap de 50 eventos no script; sem TTL mas com tamanho limitado |
| Admin key vazando pro bundle do browser | Information Disclosure | `import "server-only"` + leak-guard de teste que grepa `src/` e exige a key em EXATAMENTE 2 arquivos (`gateway.test.ts`) |
| Segredos no payload publicado (Vast key, Portainer key) | Information Disclosure | `build_payload()` deve construir o dict **explicitamente campo a campo** — NUNCA `json.dumps(env)` nem `st` inteiro sem filtro. O `state.json` hoje não guarda segredo, mas o payload é lido por qualquer operator no dashboard |
| Audit forjado / suprimido | Repudiation | `writeAuditLog` NÃO é exportado como server action (CR-02); só os `*Core` in-process chamam |
| Comando replay (operator reclica 20×) | DoS (self-inflicted) | GETDEL consome uma vez; um segundo clique antes do poll sobrescreve a mesma chave (idempotente por natureza) |

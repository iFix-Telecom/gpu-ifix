<decisions>
## Implementation Decisions

### Canal de publicação
- **D-01:** Script publica via `POST /admin/sttpod/state` com `X-Admin-Key`; gateway grava o payload no Redis `gw:sttpod:state`. NÃO expor Redis pra ops-claude; NÃO pull pelo gateway.
- **D-02:** Publica a cada ensure (15min, heartbeat) + imediatamente em provision/migrate/destroy/falha.
- **D-03:** Staleness: payload leva `published_at`; chave Redis SEM TTL; dashboard marca badge "stale" se >20min. Último estado conhecido sempre visível.
- **D-04:** Credencial: admin key existente (`ifix_admin_****613f`), adicionada em `/etc/onboard/secrets/vast-3060.env` (root-600, já usado pelo script). Zero código novo de auth.

### Histórico + custo/dia
- **D-05:** Histórico é blob no payload: script mantém lista capped de eventos no `state.json` e manda no POST; gateway guarda o JSON inteiro no Redis. ZERO migration, zero sqlc, zero tabela nova.
- **D-06:** Retenção: últimos 50 eventos (cap por contagem).
- **D-07:** Custo/dia e custo/mês calculados e acumulados pelo script no `state.json` (ele conhece $/h e períodos up); payload chega pronto, dashboard só exibe.
- **D-08:** Moeda: BRL + USD entre parênteses (consistente com o cost panel do primário, `USDToBRLRate`).

### Botões manuais (provision/destroy)
- **D-09:** Incluídos nesta fase via comando pendente: `POST /admin/sttpod/command` → gateway grava `gw:sttpod:command` no Redis → script consome e executa. Gateway NUNCA executa nada no ops-claude diretamente.
- **D-10:** Consumo do comando: poll dedicado 1-2min (timer systemd novo ou loop encurtado só pra checar comando pendente) — botão utilizável, não espera o ensure de 15min.
- **D-11:** Permissão: owner-only + dialog de confirmação, espelhando o padrão Phase 18 (owner edita / operator read-only); ação gera `admin_audit_log`.
- **D-12:** Feedback: script ecoa `pending_command`/`last_command_result` no próximo publish; card mostra "comando pendente…" → "executado às HH:MM". Sem canal/endpoint novo de status.

### Card no dashboard
- **D-13:** API: estender `GET /admin/operations` com campo `sttpod` novo na resposta agregada (uma fetch, um poll de 10s). UI: 5º painel na página `/operacao` existente. Sem rota nova no dashboard.
- **D-14:** Conteúdo do card: básico (máquina/geo, $/h, ip:porta, uptime, custo dia/mês) + `machine_avoid` list + histórico de provisions/falhas + status dos upstreams `local-stt`/`kokoro-tts` (redundância proposital com o painel de breakers) + agenda 07-22 com próxima transição (tipo o schedule panel do primário).
- **D-15:** Histórico renderizado como tabela estilo `operacao-lifecycle-timeline` (data, máquina, $/h, resultado, duração).

### Claude's Discretion

- Detalhe visual/espaçamento do 5º painel na página.

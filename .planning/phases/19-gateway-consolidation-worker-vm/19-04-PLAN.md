<objective>
Migrate the production tenant/key set from `bd_ai_gateway_prod` into `bd_ai_gateway` so the ~18 real client apps keep authenticating against the consolidated worker-vm gateway WITHOUT key regeneration. This is the irreversible DB step — it deletes the throwaway dev tenants (and their FK children) and loads prod rows. It is its own atomic plan, gated by a BLOCKING human checkpoint, with full root-owned backups for rollback.

Purpose: LOCKED decision (19-CONTEXT) — migrate tenants + api_keys (preserve HASH byte-for-byte) + admin_keys + current-period usage_counters; leave the PROD billing_events history in `_prod` as archive (research A5). Slug collisions with the dev tenants are resolved DELETE-dev-first so prod UUIDs win and api_keys FK resolves.
Output: bd_ai_gateway carries the prod tenant/key/admin/quota state, proven byte-for-byte identical and authenticating live pre-cutover (no public traffic yet).

Mechanics (Codex-review rewrite + plan-checker FK fix): NOT `pg_dump | psql` into live tables, NOT two `psql` sessions. Instead — load prod rows into a transient staging schema `ai_gateway_migration.*` in the TARGET DB, snapshot the dev tenant ids into `ai_gateway_migration.dev_tenants_to_delete`, then run ONE psql invocation of a generated `migrate.sql` (`\set ON_ERROR_STOP on; BEGIN; <NO-ACTION-child pre-deletes>; <scoped deletes>; <INSERT…SELECT staging→live in FK order, orphan-guarded>; <in-transaction verification with RAISE EXCEPTION guards>; COMMIT;`). Cross-DB `INSERT…SELECT` is impossible in Postgres, so staging-in-target is the atomic path.

FK GOTCHA the checker caught (B-1): `ai_gateway.tenants` has four FK children. THREE are `ON DELETE CASCADE` (api_keys 0002:15, usage_counters 0006:9, voices 0025:39) so the tenant DELETE drops their dev rows automatically. ONE — `billing_events` (0010:8) — is `REFERENCES ai_gateway.tenants(id)` with NO `ON DELETE` clause (= NO ACTION). The TARGET `bd_ai_gateway` holds 918 dev billing_events rows; without an in-tx pre-delete of those rows the tenant DELETE raises a FK violation and the whole transaction ROLLBACKs on EVERY run. The fix pre-deletes the dev billing_events rows inside the same transaction, before the tenant DELETE, and a `pg_constraint` preflight enumerates all non-CASCADE children so no NO-ACTION child is ever missed again.
</objective>

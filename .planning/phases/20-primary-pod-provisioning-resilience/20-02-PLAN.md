# Plan 20-02 — OBS-11: download-weights.sh mid-file heartbeat (enables FF-02)

> **Requirement ID note:** OBS-01 is already a COMPLETE v1 requirement (Phase 7,
> REQUIREMENTS.md:79). This phase's download-heartbeat requirement is **OBS-11**
> (OBS-09/10 are taken by Phase 15). ROADMAP.md already reconciled.

Today `download_and_verify()` runs `mc cp --quiet` (line 55). With `--quiet`, a single
16 GB Qwen file emits exactly TWO log lines — `fetching …` (start) and `ok …` (end) — with
NOTHING in between. During that window the onstart log (`/var/log/onstart.log`, tee'd to the
Vast console) is silent, so a download STALL mid-file is invisible. FF-02 (plan 20-04) keys
its regime-3 stall detector on the newest ISO-8601-timestamped `[download-weights]`
heartbeat line advancing; without a mid-file heartbeat it can never fire during a large
file. This plan makes the download emit a periodic progress heartbeat.

**Laziest fix that works:** drop `--quiet` so `mc cp` prints its own periodic transfer
progress line. If `mc`'s default progress is not reliably line-buffered to the tee'd log
(it uses a carriage-return-updated TTY progress bar that may not flush to a non-TTY pipe),
fall back to a lightweight background heartbeat loop that logs the destination file's
growing size every ~15s while the `mc cp` runs, killed when the copy returns. ponytail:
heartbeat loop is ~6 lines of bash; no new tool.

**CRITICAL (Codex review HIGH #1) — the signal must be progress-BEARING, not liveness.** A
periodic tick that only proves "the loop is alive" emits a fresh TIMESTAMP even while the
transfer is frozen → a hung download would "prove progress" forever and FF-02's stall would
NEVER fire. The heartbeat MUST carry the current dest-file BYTE COUNT so FF-02 can detect
"bytes not increasing between samples" = a real stall. The download bracket lines
(`fetching` / `ok`) also frame the download PHASE so FF-02 can scope its timer (arm on
`fetching`, disarm on `ok`).

<threat_model>
Attack surface: this script runs INSIDE the paid pod as root during onstart, before the
health-bridge exists. It handles MinIO creds (`MINIO_ACCESS_KEY`/`MINIO_SECRET_KEY`) already.
- **Cred leak via verbose output:** dropping `--quiet` makes `mc cp` more verbose. `mc cp`
  prints the object path + progress, NOT the alias creds (the creds live in the
  `mc alias set` line at :43, unchanged). Verify the removed-quiet output does not echo the
  endpoint credential — it prints `ifix/<bucket>/<key>` only. No new cred surface.
- **Heartbeat DoS on the log:** a 15s interval over a worst-case 60-min download is ~240
  lines/file — trivial. Do NOT log every byte or poll sub-second (would flood the tee'd
  console and the Vast logs API FF-03 fetches). Interval fixed at ~15s.
- **Orphaned background process:** a heartbeat loop that outlives the copy would keep logging
  forever and hold a PID. Mitigated by killing the captured PID on every return path
  (success and failure) — asserted by the scratch self-check.
- **False stall signal:** byte-size polling on a sparse/preallocated file could show
  no growth even while healthy. Acceptable — FF-02 treats "no heartbeat advance" as the
  stall signal and the byte-size line advances for a streaming `mc cp`; the ponytail comment
  names `mc --json` as the upgrade if this proves too coarse in UAT.
</threat_model>

# Plan 20-04 — Reconciler: coldstart fast-fail (FF-01/FF-02) + outcome-driven lists (BL-01/AL-01)

All four requirements land in ONE plan because all four edit `gateway/internal/primary/
reconciler.go` — FF-01/FF-02 inside `waitForReadyOrDestroy` (the coldstart poll loop) and
BL-01/AL-01 at the `provisionLifecycle` return (line 1438). Splitting them into parallel
plans would put two agents into the SAME file in the same wave and conflict; the suggested
"FF ‖ BL/AL" parallelism is deliberately merged here for that reason. FF-03's `OnstartLog`
(20-03) and the new budget fields (20-01) are dependencies; OBS-11 (20-02) makes FF-02's
signal real in production.

**Test idiom (no injectable clock — RESEARCH):** drive timing with `budget=0 fires on the
first poll` (the `>=`-not-`>` trick at reconciler.go:1614) + the package var
`primaryInstancePollIntervalForTest` + scripted `fakeVast.getInstanceFn`/`onstartLogFn`
sequences. Do NOT add a fake clock.

**Decision resolutions baked in:**
- **BL-01 off-by-one (Q1) → ban when `failStreak >= 1` at the failure hook.** `failStreak`
  is read at the TOP of `provisionLifecycle` (line 1292, BEFORE this attempt is counted; the
  open lifecycle row is excluded from `CountConsecutiveFailedPrimaryProvisions`). So after
  THIS attempt fails, the effective consecutive-failure count is `failStreak + 1`. To ban on
  the 2nd consecutive failure (decision #4 "ban when fail_streak≥2"), gate the blocklist
  append on `failStreak >= 1`. The `failStreak` local is already in scope at line 1438.
- **New close reasons (Q4) are free-form DB strings** (`created_state_timeout`,
  `progress_stall_timeout`) — `closeLifecycle` writes `shutdown_reason` as `pgtype.Text` to
  the DB; there is NO bounded prometheus label for primary close reasons (confirmed:
  `GatewayEmergencyLifecyclesTotal` is emerg-only; primary has none). No alerter-fingerprint
  wiring needed.
- **FF-02 cadence (Q6):** the Vast logs API is async (~seconds); do NOT fetch every ~5s
  poll. Fetch `OnstartLog` on a slower sub-cadence (every ~30s, gated by a
  `lastLogFetchedAt` check inside the loop) so it never stretches the poll tick.

<threat_model>
Attack surface: this plan decides when to DESTROY a paid Vast pod and which real Vast
machine_ids get auto-parked/preferred — a wrong predicate wastes money or bricks provisioning.
- **Billing-burn (false-negative fast-fail):** a bug that fails to anchor `firstCreatedAt`
  or mis-parses the heartbeat would let a dead pod burn to `coldstart_budget_s` (up to 90 min
  × ~$0.30-0.77/h). Mitigation: the `coldstart_budget_s` ceiling is untouched (still the
  absolute backstop); FF-01/FF-02 only ADD earlier exits; budget=0 unit tests prove the exit
  fires.
- **Over-aggressive kill (false-positive fast-fail) — the REGIME-2 hazard:** killing a
  legitimately slow-but-live cold start wastes the re-provision AND poisons the blocklist.
  Mitigations: FF-01 arms ONLY on `created`/`scheduling` and RESETS on the `loading`
  transition, so a healthy 15-min image pull (regime 2) is never touched by the created-budget
  (regression-tested by the required created→loading negative test). FF-02 arms only once the
  container is up (`running`) or onstart has logged a heartbeat, and resets on every heartbeat
  advance — an advancing download never trips. The one residual false-kill (running +
  logs-API-fully-down + healthy long download > progress_stall_budget_s) is named in the
  ponytail comment; OBS-11 heartbeats make it rare and 20-06 UAT captures the real
  actual_status to tighten if needed.
- **Blocklist poisoning / allowlist starvation:** auto-blocklisting on transient hiccups
  could park good hosts and shrink the market. Mitigations: `failStreak>=1` grace (never ban
  on the 1st failure); allowlist success removes a machine from the blocklist so a
  degraded-then-recovered host self-heals; no TTL now (manual prune, ponytail-marked) but the
  allowlist cap-20 FIFO bounds growth. Because blocklist has no auto-expiry, a permanently
  flaky-then-fixed host stays parked until manual prune — accepted, upgrade path noted.
- **Lost-update race on the two lists:** the hook reads fresh + writes; the primary is
  leader-gated (single reconciler, PRV-03) so concurrent writes are not expected. ponytail
  comment names the ceiling.
- **No secrets in this plan** (machine_ids are non-sensitive integers; the Vast key stays in
  the 20-03 client).
</threat_model>

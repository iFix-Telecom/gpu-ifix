# Plan 20-07 — Gap-closure: port-bind gate on downloadDone + FF-02 expectedWeightFiles 3→4

Two defects surfaced by the 20-06 live UAT on real Vast (both in
`gateway/internal/primary/reconciler.go`, both invisible to the unit tests because
the tests drive the timing with `budget=0` and never model the real
download-before-bind ordering). Neither changes the FSM shape — each is a targeted
correctness fix in the coldstart poll loop.

**Context (live evidence, 20-06):** a fresh (non-cached) primary coldstart downloads
~20 GB of weights (qwen 18 GB + whisper + bge-m3 + chatterbox) INSIDE the onstart
script, which runs AFTER `actual_status=running` but BEFORE llama-server binds its
public port. On lifecycle 137 this closed `public_port_bind_timeout` at ~3 min — a
FALSE kill of a healthy coldstart — because the port-bind budget (`port_bind_budget_s`,
seed 120 s) counts from `firstRunningAt` (= download start) and the download alone
exceeds it. Worked around live by PATCHing `port_bind_budget_s=600` on the pod_config
row; this plan makes the tight budget safe again so the workaround can be reverted.

## Tasks

<task type="auto">
<name>Gate the port-bind fast-fail on FF-02 downloadDone (no false-kill during download)</name>
<action>
In `reconciler.go`'s coldstart poll loop (the `waitForReadyOrDestroy` running-state
branch, ~lines 1720-1781): the two `public_port_bind_timeout` fail-fast blocks
(`if elapsed >= portBindBudget { … }` at ~1744 and ~1775) must NOT fire while the
weights download is still in progress. The FF-02 block already tracks `downloadArmed`
/ `downloadDone` (set at ~1657/1663). Add `var downloadDoneAt time.Time` alongside
`downloadDone`; set `downloadDoneAt = time.Now()` at the SAME point `downloadDone` is
set true (the `okCount >= expectedWeightFiles` case).

Change the port-bind budget anchor from `firstRunningAt` to a download-aware anchor:
- While `downloadArmed && !downloadDone` (download provably in flight): SKIP the
  port-bind timeout entirely — keep the existing per-poll Warn (so the wait is still
  operator-visible) but do NOT destroy; the download-stall detector (FF-02) owns this
  window and `coldstart_budget_s` remains the absolute backstop.
- Once `downloadDone`: measure `elapsed := time.Since(downloadDoneAt)` (NOT
  `firstRunningAt`) for BOTH port-bind blocks, so the tight `port_bind_budget_s` counts
  the post-download service-bind window as intended.
- If the download NEVER arms (telemetry unavailable — OnstartLog FetchError/Empty/NotReady,
  `downloadArmed` stays false): fall back to the CURRENT `firstRunningAt` anchor. This
  preserves the existing "telemetry-unavailable rides to the ceiling" philosophy AND keeps
  port-bind fast-fail working when there's genuinely no download signal. Document this
  three-way anchor with a `// ponytail:` comment naming the trade-off.

Keep the `>=` (not `>`) comparison so a `budget=0` unit test still fires on the first
qualifying poll. Do not touch `coldstart_budget_s` (backstop) or the FF-01 created anchor.
</action>

<threat_model>
Attack surface: this plan changes WHEN a paid Vast pod is destroyed during coldstart.
- **False-negative (weakened fast-fail):** gating port-bind on downloadDone means a pod that
  reaches running, arms the download, then hangs mid-download is caught by FF-02 (byte-frozen),
  not port-bind — and if FF-02's telemetry is unavailable it rides to `coldstart_budget_s`.
  Mitigation: `coldstart_budget_s` is untouched (absolute backstop); the telemetry-unavailable
  fallback keeps the legacy firstRunningAt port-bind anchor so a no-signal pod still fast-fails.
- **False-positive (over-kill) is REDUCED, not added:** the whole point is to stop killing
  healthy downloads. The post-download anchor only starts the tight clock once the service
  could plausibly bind.
- No new external surface, no new deps, no migration.
</threat_model>

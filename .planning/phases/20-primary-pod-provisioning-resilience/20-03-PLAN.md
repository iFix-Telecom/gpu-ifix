# Plan 20-03 — FF-03: Vast logs API client method (regime-3 progress source)

FF-02 (plan 20-04) needs to read the pod's onstart-log heartbeat WHILE the weights download
runs — before the `:9100` health-bridge exists, when the only external signal is
`actual_status` + the onstart log. This plan adds the PRIMARY progress source: a Vast logs
API client method that fetches `/var/log/onstart.log` content asynchronously
(`PUT /api/v0/instances/request_logs/{id}/` → response `result_url` → `GET result_url`).

**Scope decision (Q3 — SSH-tail DEFERRED):** the CONTEXT fallback chain is
(a) Vast logs API → (b) SSH-tail `/var/log/onstart.log`. There is NO Go SSH client in the
reconciler (only `pod/scripts/vast-ai.sh ssh-exec` in bash). Adding `x/crypto/ssh` or
shelling out to `ssh` is net-new surface for a FALLBACK. CONTEXT §Claude's Discretion allows
leaning 100% on the logs API. **This plan ships ONLY leg (a) in Go.** The SSH-tail fallback
is deferred to a follow-up quick-task and only built if the HUMAN-UAT (20-06) proves the
Vast logs API unreliable. `// ponytail: SSH-tail fallback deferred — Vast logs API is the
sole progress source; add x/crypto/ssh or shell-out to vast-ai.sh ssh-exec only if 20-06
shows the logs API drops heartbeats.`

**Mirror exactly:** `GetInstance` (client.go:249-293) for URL build / `setAuthHeader` /
`httpClient.Do` / metrics / `parseErrorBody`. The key touches the request ONLY via
`setAuthHeader` (never logged — `TestClientNeverLogsAPIKey` enforces this over the source).

**result_url shape (Q2 — OPEN, validate in 20-06):** the async `PUT → result_url → GET`
contract is asserted by CONTEXT decision #1 but the response BODY shape is unverified
in-repo. Code DEFENSIVELY: decode the PUT response for a `result_url` string field
(tolerate `success`/`msg` wrapper keys like the other Vast envelopes); if `result_url` is
absent/empty, return a typed "logs not ready yet" signal (NOT an error that kills the
provision). The GET fetches the raw log text. `// ponytail:` note that the exact JSON keys
are UAT-confirmed in 20-06.

<threat_model>
Attack surface: a new client method that hits the Vast API (authenticated) and then GETs a
Vast-returned `result_url` (attacker-influenceable if Vast or the network is compromised).
- **Cred leakage:** the API key rides ONLY `setAuthHeader` on the PUT to the Vast host. The
  `result_url` GET must NOT carry the key (it is presigned); attaching it to an off-host URL
  would leak the bearer to whatever host Vast names. Mitigation: only set the auth header on
  requests to `c.baseURL`; the result_url GET goes out key-less. Asserted by
  TestClientNeverLogsAPIKey + a test that the GET handler sees no Authorization header.
- **SSRF via result_url:** Vast controls `result_url`; a malicious/compromised response
  could point it at an internal address. The GET runs from the gateway with the shared
  30s-timeout client. Mitigation for v1: bounded `io.LimitReader` (256 KiB) caps the read;
  the content is only scanned for a heartbeat timestamp, never executed or reflected. Full
  SSRF hardening (allowlist result_url host to vast.ai/*.cloudflarestorage) is a `ponytail:`
  upgrade noted for 20-06 if the observed result_url host is stable.
- **Billing-burn:** this method is READ-ONLY — it cannot create/destroy instances. It adds
  Vast API calls; FF-02 (20-04) throttles the call cadence (every Nth poll) so it does not
  hammer the API or stretch the poll loop.
- **Heap flood:** an upstream returning a giant log body is capped by LimitReader.
</threat_model>

# Plan 20-03 — FF-03: Vast logs API client method (regime-3 progress source)

FF-02 (plan 20-04) needs to read the pod's onstart-log heartbeat WHILE the weights download
runs — before the `:9100` health-bridge exists, when the only external signal is
`actual_status` + the onstart log. This plan adds the PRIMARY progress source: a Vast logs
API client method that fetches `/var/log/onstart.log` content asynchronously
(`PUT /api/v0/instances/request_logs/{id}/` → response `result_url` → `GET result_url`).

**FF-03 is SPLIT (Codex review HIGH #5) — this phase ships leg (a) only:**
- **Leg (a) — Vast logs API in Go (THIS phase).** `PUT /instances/request_logs/{id}/` →
  `result_url` → `GET result_url`.
- **Leg (b) — SSH-tail `/var/log/onstart.log` (DEFERRED follow-up, ROADMAP/CONTEXT amended).**
  There is NO Go SSH client (only `pod/scripts/vast-ai.sh ssh-exec` in bash); adding
  `x/crypto/ssh` or shelling out is net-new surface for a fallback.
- **Deferring SSH is SAFE because of finding #3 (telemetry-unavailable = UNKNOWN, non-fatal):**
  a logs-API outage makes `OnstartLog` return `Status=fetch_error`, which FF-02 treats as
  UNKNOWN → it does NOT fast-fail → regime 3 simply RIDES to the `coldstart_budget_s` ceiling
  (the safe default), NEVER a false kill. So the only cost of no-SSH-fallback is "regime 3
  fails slow instead of fast during a Vast logs outage" — acceptable; SSH-tail closes that
  gap later. `// ponytail: SSH-tail fallback deferred; leg-(a) fetch_error is non-fatal so
  the worst case is ride-to-ceiling, not a false destroy.`

**Mirror exactly:** `GetInstance` (client.go:249-293) for URL build / `setAuthHeader` /
`httpClient.Do` / metrics / `parseErrorBody`. The key touches the request ONLY via
`setAuthHeader` (never logged — `TestClientNeverLogsAPIKey` enforces this over the source).

**Return a STATUS enum, not bare text (Codex review HIGH #3).** FF-02 must distinguish "we
saw the log and it says X" from "we could not read the log". `OnstartLog` returns an
`OnstartLogResult{ Status OnstartLogStatus; Text string }` where
`OnstartLogStatus ∈ {Available, NotReady, FetchError, Empty}`:
- `Available` — GET returned non-empty log text (`Text` set).
- `NotReady` — PUT returned no `result_url` yet (async result still cooking) — NORMAL, non-fatal.
- `FetchError` — PUT or GET failed (Vast logs API down/delayed/transport error) — UNKNOWN, non-fatal.
- `Empty` — GET returned 200 but empty/whitespace body — UNKNOWN, non-fatal.
FF-02 fast-fails ONLY on `Available` + provably-frozen bytes; every other status = ride to
the ceiling. Transport/API failures are FOLDED into `Status=FetchError` (the returned `error`
is for truly unexpected cases only; FF-02 branches on `.Status`, not the error).

**result_url shape (Q2 — OPEN, validate in 20-06):** the `PUT → result_url → GET` body shape
is unverified in-repo. Decode DEFENSIVELY for a `result_url` string (tolerate `success`/`msg`
wrapper keys like other Vast envelopes); absent/empty → `Status=NotReady`. **SSRF guard
(finding #8):** before the GET, require `result_url` scheme == `https`; keep NO auth header on
the GET (presigned). `// ponytail:` the exact JSON keys + a host-allowlist for `result_url`
are UAT-confirmed in 20-06 (host-allowlist is a REQUIRED 20-06 follow-up once the real host is observed).

<threat_model>
Attack surface: a new client method that hits the Vast API (authenticated) and then GETs a
Vast-returned `result_url` (attacker-influenceable if Vast or the network is compromised).
- **Cred leakage:** the API key rides ONLY `setAuthHeader` on the PUT to the Vast host. The
  `result_url` GET must NOT carry the key (it is presigned); attaching it to an off-host URL
  would leak the bearer to whatever host Vast names. Mitigation: only set the auth header on
  requests to `c.baseURL`; the result_url GET goes out key-less. Asserted by
  TestClientNeverLogsAPIKey + a test that the GET handler sees no Authorization header.
- **SSRF via result_url:** Vast controls `result_url`; a malicious/compromised response
  could point it at an internal address. The GET runs from the gateway with the shared
  30s-timeout client. Mitigations shipped here: (1) require `scheme == "https"` before the GET
  (rejects `file://`, `http://` internal, etc.); (2) bounded `io.LimitReader` (256 KiB); (3)
  content is only scanned for a heartbeat timestamp, never executed or reflected. A
  `result_url` HOST allowlist (e.g. vast.ai / *.cloudflarestorage) is a **REQUIRED 20-06
  follow-up** (finding #8) once the real result_url host shape is observed in the first
  live coldstart — promoted from "maybe later" to a must-do.
- **Billing-burn:** this method is READ-ONLY — it cannot create/destroy instances. It adds
  Vast API calls; FF-02 (20-04) throttles the call cadence (every Nth poll) so it does not
  hammer the API or stretch the poll loop.
- **Heap flood:** an upstream returning a giant log body is capped by LimitReader.
</threat_model>
